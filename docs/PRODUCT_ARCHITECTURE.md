# 汽车副屏：产品与系统总体规划

> 2026-09-08：用户已改选 P4 Function EV Board v1.4 主线，S3 平台不再支持。
> 本文保留为历史评估，以下 S3/Linux/CarPlay 路线不再代表当前决定。
> 当前设备端实现与限制以 [P4 上板与联调](P4_BRINGUP.md) 和根 README 为准。

版本：2026-09-07。状态：方案设计，不代表已实现或通过量产认证。

本稿合并车辆参数显示、诊断记录、手机热点联网、远程修复、音乐播放、CarPlay 候选能力和驾驶员状态辅助提醒。
正常运行时副屏作为 Wi-Fi STA 连接手机热点；手机承担互联网出口，不承担日志代理程序。
工程仍只保留 ELM327 BLE 车辆数据入口，不恢复开发板直连车辆总线，不创建 `projects` 目录，当前 S3 构建继续使用根 `build`。

## 1. 产品决策

定位：面向老式燃油车的 7 寸增补信息与媒体终端。离线仍可显示已支持的车况；联网用于售后诊断、配置和升级，不替代原车仪表或驾驶员责任。

- 当前验证平台：继续用现有 S3 板完成采集、记录、Wi-Fi STA 上传和 OTA 闭环，不为这些能力先换主控。
- 正式完整版优先路线：成熟 Linux 投屏主机平台 + 独立 ESP32-S3 车辆采集 MCU。先评估可用于本产品的 CarPlay/Android Auto 方案、SDK 和授权路径，再确定应用处理器及 PCB。
- 无 CarPlay 的备选路线：P4 + C6 + 独立经典蓝牙音频模块，适合仪表、多媒体及轻量视觉验证，但不作为通往 CarPlay 的必经升级。
- 不同时展开 S3、P4、Linux 三条量产产品线。S3 是当前验证平台；正式主板在投屏方案评估门槛通过后冻结。
- 手机音乐首个验证选 A2DP Sink + AVRCP，即普通蓝牙音箱体验；通话需要另行验证 HFP、麦克风和回声消除。
- 不把摄像头首发功能命名为“可靠疲劳预警”。先验证驾驶员可见性和持续头部偏离，闭眼等功能须进一步测量。

正式 SKU 建议共享同一主板及升级系统，基础款不装驾驶员摄像头，增强款增加摄像头与本地视觉能力。
触屏版和旋钮按键版共用数据模型与导航事件；非触屏投屏体验必须在供应商 SDK 中单独验收。

## 2. 能力现状与边界

| 能力 | 当前工程 | 本规划新增 |
| --- | --- | --- |
| 车辆采集 | NimBLE 自动扫描/重连，ELM 初始化，CAN 协议 6/7/8/9，10 项标准参数 | 更多标准字段、车辆能力档案、经验证的扩展配置 |
| UI | 五页、三配色、中文、手动切换、实时与演示隔离 | 问题记录、联网/升级状态、媒体页、辅助提醒 |
| 记录与云端 | 没有用户诊断包、上传服务和历史日志回放 | 本地有界记录、上传队列、工单、回放和发布后台 |
| 更新 | 单应用分区，有线烧录 | 双应用槽 OTA、配置包双副本、签名与回滚 |
| 音频/投屏/摄像头 | 未实现 | 分阶段硬件与软件集成，不靠现有 UI 预留项冒充可用 |

现有板端扫描通过不等于已经完成真实适配器和车辆联调。原始 ELM 数据是指令和 ASCII 响应，不能把它当成全车 CAN 总线的完整抓包。
部分老车使用非 CAN 诊断协议；ELM 芯片支持不代表当前固件已经支持。新增协议需独立实现和回放验收，未知车型保持不可用。
协议边界参考 [ELM327 官方手册](https://elmelectronics.com/wp-content/uploads/2020/05/ELM327DSL.pdf)。

## 3. 总体连接

```text
Vehicle <-> ELM327 -- BLE --> Vehicle collector MCU
                                  |
                                  +--> Decoder --> Validated data --> Dashboard
                                  |
                                  +--> Raw recorder --> Local durable queue
                                                            |
Dashboard network manager -- Wi-Fi STA --> Phone hotspot --> Internet
                                                            |
                                     HTTPS <--> Cloud API / Object storage
                                                    |
                                            Support / Replay / CI
                                                    |
                                     Signed profile / Signed firmware
```

S3 验证版的采集、UI、记录和联网都在当前 MCU 内。完整版则由独立 S3 负责 BLE、解析和短时记录，Linux 主机负责屏幕、持久存储、STA、媒体和云端。
两芯片通过有帧边界、版本号、序列号、CRC 和流控的 UART/SPI 通道交换数据与日志；禁止 Linux 任意透传诊断控制命令。
正式版只选一个主要 STA 联网负责人，避免 Linux 和 S3 同时扫描手机热点。Linux 重启时 MCU 可继续短时记录，但不能据此承诺屏幕仍正常显示。

P4 备选版可使用官方 ESP-Hosted 的无线协处理器架构；它与具体 C6 固件/IDF 版本存在依赖，要固定版本后验证，不能默认现有 S3 工程无改动运行。
官方 P4 开发板提供屏幕、摄像头和无线协处理器的参考，见 [P4 Function EV Board](https://docs.espressif.com/projects/esp-dev-kits/en/latest/esp32p4/esp32-p4-function-ev-board/user_guide.html)。

## 4. 联网与用户操作

### 首次设置

1. 用户在屏幕输入手机热点名称和密码，选择 2.4 GHz 兼容模式，随后设备以 STA 连接。
2. 非触屏版可提供一次性的配网 AP 页面，完成后关闭 AP；这是维护入口，不改变正常 STA 工作方式。
3. 联网后显示一次性绑定码，用户在云端网页绑定自己的设备；设备本身使用独立凭据认证，不能把设备编号当密码。
4. 用户单独选择是否上传匿名诊断、是否允许某次完整日志、蜂窝流量上限；摄像头数据不包含在普通同意项内。

S3 和 C6 的 Wi-Fi 路线需要考虑 2.4 GHz 热点；iPhone 的“最大兼容性”会限制到 2.4 GHz，见 [Apple 热点安全说明](https://support.apple.com/en-ca/guide/security/secfd166f620/web)。
热点开启、锁屏、省电、无移动数据和重新上车均需实测，不承诺设备能强制唤醒或开启手机热点。
手机浏览器无需访问自己的热点客户端 IP 即可查看云端工单；不依赖 mDNS 或热点允许客户端互访。

### 日常运行

- 车辆链路优先：先维护仪表有效数据和告警，再处理后台网络；没有互联网不影响已有本地功能。
- STA 状态区分未配置、寻找热点、认证失败、已连局域网、互联网可用、上传排队。连上 Wi-Fi 不等于服务器可达。
- 无网先落盘，联网后限速上传；鉴权失败停止重试并提示，网络错误使用带随机抖动的退避。
- 第一版默认停车后上传大日志和下载升级，驾驶中只允许用户已授权的小型状态摘要。
- 提供热点密码更新/删除、忘记设备、停止分享和本地导出入口。不开放路由器端口，不要求用户暴露电脑。

Wi-Fi 和 BLE 会争用射频时隙，不能视为互不影响的链路；首版需要共存配置、有限扫描和上传限流。
见 [Espressif RF 共存说明](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-guides/coexist.html)。

## 5. 记录器设计

### 三种记录

| 模式 | 默认策略 | 目的 |
| --- | --- | --- |
| 日常统计 | 低频数值、有效性和事件；有限保留 | 行程趋势、数据缺失统计，不保存无限原始数据 |
| 异常窗口 | 内存环形缓冲，触发后封存前后窗口 | 断线、超时、解析失败发生前后的现场 |
| 用户问题记录 | 用户停车开始，限定时长与容量，自动停止 | 完整包含连接、初始化、支持位图及实际响应 |

建议先以 256-512 KiB 的 S3 原始记录内存预算压测；能覆盖多久由真实记录速率决定，不写死“必有几分钟”。
长期日志存储不能放在普通 NVS 键值区反复追加。验证版需规划专用分区和磨损策略；完整版使用 eMMC/高耐久 SD，并验证突然掉电行为。
缓存满时发布丢失计数和缺口事件，不能悄悄覆盖后把诊断包标成完整。活跃、封存、上传文件分离。

### 每条记录的字段

- 基础：记录格式版本、单调时间戳、启动会话、序列号、事件类型；校时后另外记录 UTC 映射与校时状态。
- 会话：连接代次、指令事务编号、ECU 来源、运行模式、所用配置版本、重连/超时/截断原因。
- 原始通信：实际 TX 字节、写入提交/完成结果、原始 RX 字节、通知编号、原始长度和内部拆分偏移。
- 能力与环境：适配器标识/固件报告、GATT 布局、AT 初始化响应、协议、各响应 ECU 的支持位图。
- 派生值：字段键、值、单位、采样时刻、有效/过期、估算标记及失败原因，不用假零代替未读到。
- 问题描述：车型、年款、发动机/变速箱版本、问题时刻和用户观察；不要只填一个品牌名称。

原始记录必须发生在大小写转换、去空白和拼接之前。BLE 回调只做有界内存拷贝，不写文件、不压缩、不上传、不调用 LVGL。
通知到日志队列的丢失与通知到解析队列的丢失分别计数。记录器错误不得改变采集事务顺序。
导出格式建议 JSONL + 原始字节 hex/base64；设备存储可用带长度、CRC 和版本的紧凑二进制，导出时转换。
设备原始日志不能直接按 DBC 解析；可另行导出已确认的诊断 CAN 响应帧，但应标明并非全总线记录。

### 诊断包

```text
report/
  manifest.json    # schema, build, hardware, profile, capabilities, integrity
  traffic.jsonl   # TX/RX, exact bytes, time, session and transaction
  events.jsonl    # errors, reconnects, resets, logging gaps
  metrics.csv     # optional human-readable values and validity
  notes.json      # user description and explicit sharing choices
```

摄像头内容默认不进入上述诊断包。VIN、完整蓝牙地址等默认不采集或在协议感知的导出步骤处理；将来允许私有原始响应时，不能保证任意未知字节已自动脱敏，必须另行授权。
时间序列也可能揭示使用习惯，上传前显示内容类别和大小，并提供删除功能。

## 6. 上传与云端售后

设备通过手机热点主动发起 HTTPS 请求。第一版采用 HTTPS API、对象存储、元数据数据库和后台任务，不需要远程桌面或永久控制通道。

上传状态为 `recording -> sealed -> queued -> uploading -> verified`。封存文件不可再修改；每个报告有随机 report_id、分块编号、长度和 SHA-256。
断网从已确认的块继续，重复上传幂等处理；服务端验证整个文件并确认之前，设备不能仅凭“已发送”删除本地包。
设备分配独立证书或密钥，验证服务端 TLS 证书。凭据不进入日志；凭据轮换与撤销要覆盖设备转让和丢失。

后台第一版包含五个工作区：

| 工作区 | 必须具备的能力 |
| --- | --- |
| 设备 | 所有者、硬件/固件/配置版本、联网状态、上传授权 |
| 工单 | 问题描述、报告关联、处理状态、用户反馈 |
| 日志 | 完整性与缺口、事务时间线、ECU 能力、解析前后对照 |
| 车型配置 | 已验证的参数来源、版本、适用 ECU/动力系统、回归样本 |
| 发布 | 签名产物、目标硬件、测试/灰度/正式渠道、撤回和成功率 |

建议初始运维策略为普通上传每天每台最多 20 MiB、单次诊断包最多 10 MiB、云端原始包默认保留 30 天；这些是可调整的产品建议，不是实测需求。
用户可降低/关闭流量额度，异常窗口不无限堆积；已上传旧包优先淘汰，未上传包达到上限时明确报告。
云端限制包大小、解压比例、路径和解析时间，在隔离任务中处理不可信日志；开发者能读报告不代表有权任意控制车辆。

## 7. 修复闭环与车型配置

```text
User report -> Validate and redact -> Replay existing parser
            -> Reproduce issue -> Fix profile or common code
            -> Replay all compatible test fixtures -> Sign release
            -> Targeted rollout -> Device self-test -> User verification
```

回放必须检查请求和响应事务匹配，支持原时序、加速时序、重分片及错误注入。未录到的新请求显示“无样本”，不能拿别的响应补足。
纯回放不能代替 BLE 加密/射频、车辆响应新请求、休眠和真实传感器数值验证。新增 PID 需要用户另行运行经过审核的采集计划。

车型配置包括 ECU 地址、服务/PID、返回长度、字节与位段、大小端、符号、比例偏移、单位、合法范围、轮询和失效时间。
配置只使用受限的解码表达和经过审查的只读请求，不运行脚本，不接受后台任意发送十六进制控制指令，不暴力扫描私有服务。
按平台、动力系统与 ECU 标识匹配；证据不足时回到通用标准参数，由用户确认候选车型，不能只凭 VIN 或品牌强配。
每个显示值保留来源、有效性和估算身份，未支持数据不因新配置存在而冒充可用。

区别两类更新：参数、来源与超时修正用配置包；协议引擎或驱动修复用固件。S3 与 P4/Linux 不是同一个可烧录二进制，但可以共用数据契约、车型定义和测试样本。

## 8. 升级与供电

当前是 1500 KiB 单应用分区，不具备本规划的双槽 OTA。第一阶段必须先备份必要配置，设计新分区并做一次有线迁移；不把“在线改分区表”当常规升级。
现有 16 MiB Flash 可评估两个应用槽、otadata、NVS/密钥、配置 A/B 和日志区；槽大小必须以加入网络/TLS 后的最大固件及增长余量测算，本文不直接下发分区表。

OTA 流程：检查签名清单与硬件兼容性、稳定供电和维护条件，写入非活动槽，验证长度/哈希/签名，再切换启动槽。
首次启动执行有界自检，失败回滚；不依赖云端在线或车辆必须在场才允许自检通过。配置采用独立 A/B 副本、原子切换和上一版本恢复。
模型和 UI 资源也要有兼容版本、完整性及可回退的副本，不能只回滚程序却留下不兼容资源。
这些原则对应 [ESP-IDF OTA](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/ota.html)，也已对照本机 IDF 5.5.5 的 OTA 文档。

行驶中不安装或重启。首版要求用户确认停车并保持稳定电源；没有可靠驻车数据时不能把“车速没读到”当成停车。
不要在 ACC 断电后立刻开始升级；掉电保持电路主要保障日志封存，不承诺支撑完整 OTA。
默认不远程更新 bootloader、分区表或烧写 eFuse。量产安全启动/加密与密钥生命周期单独评审，保留受控有线救援。

完整版的 Linux、采集 MCU、无线协处理器、投屏模组和模型可能各有版本。先固定协处理器固件，建立主从兼容矩阵；后续多芯片更新需要明确顺序、独立恢复路径和失败回滚，不能把依次刷两个文件称为原子更新。

## 9. 音乐与 CarPlay 的选择

| 路线 | 体验 | 本项目取舍 |
| --- | --- | --- |
| 经典蓝牙 A2DP + AVRCP | 手机音乐输出、播放控制、可支持曲目信息 | 近期音乐验证优先；无需专用手机 APP，具体信息能力依模块而定 |
| 自定义 Wi-Fi 音频/播放器 | 设备播放音频或接收特定应用流 | 不作为首发，不等于任意手机 APP 的系统投送 |
| AirPlay / CarPlay / Android Auto | 协议定义的投送或车载投屏体验 | 需专门接收端、协议和产品资质路线，不是增加 STA 就自动获得 |

S3 和 C6 只有 Bluetooth LE，不能直接作为经典蓝牙 A2DP 接收器，见 [Espressif 蓝牙能力表](https://docs.espressif.com/projects/esp-idf/en/latest/esp32c6/api-guides/bt-architecture/overview.html)。
P4 提供多媒体外设，但其 H.264 编码能力不等于完整 CarPlay 接收解码与投屏协议栈，见 [P4 H.264 编码接口](https://docs.espressif.com/projects/esp-vision/en/latest/esp32p4/api-reference/h264.html)。
结论是现有板不能通过本次固件增加就承诺 CarPlay，换 P4+C6 也不能作这种承诺；外接成熟投屏方案并非物理上不可能，但显示、输入、音频和网络集成成本必须评估。

CarPlay 车机集成与 iPhone CarPlay APP 开发是两件事；商业产品需明确 MFi/供应商授权和整机认证责任，不能把买到模块等同于自己整机已获认证。
见 [Apple CarPlay](https://developer.apple.com/carplay/) 与 [MFi FAQ](https://mfi.apple.com/en/faqs)。Android Auto 同样需从方案供应商核对接收端集成及商用要求，不把 Android Auto 与运行 Android 系统混为一谈。

若 CarPlay 确认为卖点，优先采购可评估的成熟 Linux 投屏平台，要求提供视频解码、屏幕接口、触摸/旋钮输入、媒体控制、音频焦点和升级 SDK。
普通“有线转无线 CarPlay 盒子”通常依赖原车已有接收端，不能未经验证就当成裸屏驱动主板。
自己的车况页与 CarPlay 先做整页切换，不承诺可以任意覆盖 CarPlay 画面或修改其 UI。

### 无线投屏与热点

无线 CarPlay 使用手机 Wi-Fi 连接，参见 [Apple 连接说明](https://support.apple.com/guide/iphone/connect-to-carplay-iph6860e6b53/ios)。
不能假定同一手机在无线 CarPlay 工作时，仍能以所需模式稳定提供个人热点；也不能假定主机单 Wi-Fi 接口可同时承担所有 AP/STA 角色。
优先验证有线 CarPlay + 手机热点 STA。无线方案必须实测手机型号/系统/主机方案组合；如不支持同时运行，停车后退出投屏再连接热点同步，或以后增加独立联网选件。
选配双无线接口也不能自动解决手机侧限制，须以实际方案验证，不写成产品既定能力。

### 音频硬件与路由

近期原型可接独立 A2DP/AVRCP 模块，通过 UART 控制、I2S/模拟音频送往编解码与功放。BM83 是可研究的官方参考，并非已选定 BOM，见 [Microchip BM83](https://onlinedocs.microchip.com/oxy/GUID-414904F5-364E-4377-B959-9226AD29D6A9-en-US-7/GUID-D012A5AD-8526-442A-BC43-08E7263762C7.html)。
完整版优先复用投屏平台已经验证的蓝牙音频功能，避免再堆一套重复音频主控。
推荐基础机内置提示扬声器，并通过 AUX/Line Out 接原车音响；没有 AUX 时内置扬声器可播放音乐，但音质、音量和箱体需实测，不宣传未经验证的音响效果。
双声道音响版再加独立腔体、功放、电源和散热。麦克风优先用于通话/语音，默认不开持续录音。
音频焦点统一管理：安全提示、通话/导航提示、音乐的压低与恢复；不混播两个媒体源。手机媒体输出与通话输出必须分开验收。

## 10. 摄像头与驾驶员辅助提醒

摄像头朝向驾驶员，优先考虑可调角度的小型独立模组，避免屏幕朝向变化使脸部离开视野。夜间方案要评估近红外成像与补光，不能只选一颗普通彩色摄像头。
镜头、视场、装配位置、不同身高/坐姿、眼镜与太阳镜、逆光和夜间共同决定效果；近红外补光需光生物安全和热设计评估。

第一阶段仅做人脸可见性、摄像头遮挡和持续头部偏离的研究性提醒。眼部状态、长闭眼、打哈欠和综合疲劳属于后续经验证功能，不能从演示帧率推导安全效果。
算法流水线：图像质量检查、人脸/关键点、状态与置信度、时间窗口和迟滞、事件与提示。遮挡或低置信度时显示“暂不可用”，不显示“注意力正常”。
P4 可用于轻量模型验证，官方 [ESP-WHO](https://github.com/espressif/esp-who) 是人脸检测/识别基础，不是开箱即用的车规驾驶员监控系统。
完整版按模型实测结果决定 Linux 平台是否需要 NPU 或独立视觉模块；核心提醒必须离线运行，不把云端视频推理作为唯一判断链路。

默认不保存、不上传视频和音频，仅保存经授权的事件类型、持续时间、模型版本、质量状态及时间戳。
用于算法改进的视频是另一个明确授权功能：显示录制指示、限定时长、加密保存、用户可预览/删除、单独流量配额，不能被普通“发送诊断”偷偷带上云。
建议设置物理遮挡/断电开关及与摄像头工作状态一致的指示；关闭后不继续后台采集。不得用驾驶员识别作为首发必需功能。
测试需覆盖不同人员、光照、佩戴物、安装和正常驾驶动作，并统计误报/漏报与不可用时长；不诱导用户疲劳驾驶来提供样本。
可参考 [Euro NCAP 驾驶员监测测试框架](https://www.euroncap.com/safe-driving/) 组织验证，但引用框架不表示本产品已符合或获得认证。

## 11. PCB、结构与供电

| 模块 | 设计要求 |
| --- | --- |
| 屏幕 | 7 寸、日夜可读、自动/手动亮度；分辨率先跟投屏 SDK 协调，避免后期强行缩放 |
| 现有 AT070TN94 候选 | 按实际供应商数据手册核对 RGB 时序、连接器、背光和触摸叠层；不假定能直接插到 P4 或 Linux 开发板 |
| 采集 MCU | 保留独立 BLE、看门狗与有线恢复；不把 MCU 当车规安全控制器 |
| 主机/存储 | 投屏和模型的实际负载决定内存；长日志与模型用 eMMC/高耐久 SD，不依赖大容量内部 RAM |
| 音频 | 编解码/功放/提示扬声器/AUX 路径、麦克风、静音和弹音处理、接地噪声验证 |
| 摄像头 | 独立接口和供电控制，隐私指示，若走 MIPI 不随意延长未验证的线缆 |
| 电源 | 保险、反接、瞬态、冷启动压降、EMI、稳压、ACC/电源状态输入与低功耗策略 |
| 结构 | 抗振、防眩光、热浸、支架与不遮挡视线；功放热源避开摄像头和射频 |
| 非触屏输入 | 音量旋钮、确认/返回键，停车设置无需依赖坏掉的触摸屏 |

优先使用受控 ACC 供电或合适的车载稳压附件，不能把车辆 12 V 直接接开发板。
ELM 常接常电诊断口，需要适配器休眠、掉线退避和停轮询策略；不要仅凭转速为零判熄火，自动启停也是正常场景。
分别测量整机和 ELM 的停车电流，并确认是否长期唤醒 ECU。目标市场的电气、无线、音频、隐私和安装要求应在硬件冻结前评审。

## 12. 软件边界

逻辑模块依次为 `transport`、`session`、`decoder/profile`、`vehicle_store`、`recorder`、`network`、`uploader`、`update`、`audio`、`vision`、`ui`。
这是后续职责划分，不要求现在创建空模块或重构现有目录。

- UI 只消费带时间与有效性的模型；协议标识仍留在诊断记录，不回到主界面。
- 车辆请求始终由一个调度者串行发送；记录器、云端、配置工具不另起并行请求绕过它。
- 网络、文件和图像任务有边界队列、内存上限及独立故障状态；不能通过互相持锁拖住仪表。
- 策略优先保障有效数据和告警，然后音频连续性/视觉时限，最后后台上传；准确任务优先级按测量配置。
- 不写“摄像头、音乐、上传全开也保证指标”的空承诺，整套并发负载必须一起压测。

## 13. 分阶段交付与验收

| 阶段 | 实际交付 | 退出条件 |
| --- | --- | --- |
| P0 链路基线 | 当前 S3 + 指定真实 BLE 适配器 + 至少一辆验证车 | 支持位图、数值对照、重连、点火/熄火行为可复现；补齐当前实车证据 |
| P1 诊断闭环 | 原始记录、手机热点 STA、上传 API/存储、工单和 PC 回放 | 用户问题可在电脑复现；断网恢复、重复上传、损坏包、日志满不影响采集 |
| P2 可维护版本 | 有线分区迁移、双槽 OTA、签名配置、灰度渠道 | 写入/切换阶段掉电可恢复；错硬件/错签名被拒绝；旧版可回退 |
| P3 产品平台决策 | A2DP 音频样机 + 成熟投屏平台评估 | 手机音乐/通话路由、CarPlay 资质与 SDK、热点并发、屏幕与输入路径有证据 |
| P4 正式硬件样机 | 选定一种主机平台、采集 MCU、存储与音频 | 连续运行、热/电源/射频共存、安装及服务升级验证 |
| P5 视觉增强 | 本地可见性/偏离提醒、隐私开关和事件记录 | 定义适用范围，达到评审确定的误报/漏报与不可用率，再决定发布功能名 |

P3 的投屏供应商调查应尽早与 P1/P2 并行，但正式主板不要在它完成前冻结。
首版 APP 非必需：屏幕配网、设备绑定网页、云端工单已可闭环。后续只有更强的配网、通知或用户行程需求才新增原生 APP。
建议先做一轮完整用户流程：发现问题、授权记录、热点上传、远程复现、定向发布、停车升级、用户确认，再增加娱乐和视觉负载。

### 必测场景

- 至少覆盖声明支持的每款适配器、多个车辆平台和 ECU 响应形式；不能把少量样本称为全车型兼容。
- Android/iPhone 热点、锁屏、省电、密码改变、无蜂窝网络、弱信号、热点关闭重开；开启媒体后重新测试。
- 日志队列满、文件写入失败、存储满、断网重复提交、证书/时钟问题、服务器不可用。
- 升级下载中、写入中、首次启动中掉电；错芯片包、资源版本不匹配、主从固件不兼容。
- 摄像头不可用、音频抢占、Linux 重启、MCU 重启；所有丢失数据均明确呈现，不能沿用旧值冒充实时。

## 14. 下一个实际开发范围

先在当前工程实现 P1 的设备侧：原始记录与封包、STA 配置/重连、上传持久队列、受控上传客户端，以及 PC 回放工具。
服务端配套提供最小的设备认证、分块上传确认、报告列表和版本查询。云端域名、账户/设备凭据、保存周期与流量默认值在部署前确认。
P2 单独设计分区、签名和掉电测试；本规划不直接修改 SDK 配置、不自动烧录，不购买开发板、云服务或投屏模块。
硬件采购前必须拿到投屏方案 SDK 和授权/认证责任说明，并演示它驱动目标分辨率屏幕及接收触摸/旋钮事件，不能仅凭商品页中的“支持 CarPlay”下单。
